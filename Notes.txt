3. BUG — 7 routes return 0 rows (airport code vs city code)
Problem:

 None of these routes are genuinely empty — all have data under the city code.

      prices_for_dates:  return_transfers = 0, origin_airport = YHM, link = ...search_date=29092026...

Why each one matters:

  often cheaper, and before this the data could not tell them apart.

Where each one comes from:
                       found_at                    return_stops        origin/destination_airport
  month-matrix         found_at (exact time, UTC)  -                   -
  latest               found_at (exact time, UTC)  -                   -
  prices_for_dates     search_date in `link`       return_transfers    origin_airport / destination_airport
                       (day only, e.g. 29092026)
  calendar / cheap     -                           -                   -
  ("-" = the endpoint does not send it -> saved as empty)

      - read them in normalize_month_matrix / normalize_latest_prices / normalize_prices_for_dates / _base_snapshot
      - new helper _found_date_from_link() pulls search_date out of the prices_for_dates link

  - Files: `fetch_snapshots.py` (_dedupe_key) and `fetch_multi.py` (_row_key)

3. CHANGE — month-matrix `stops` on round trips + new max_stops column

      way there only          fails 35 cases
      way there + way back    fails 40 cases
      max(there, back)        fits ALL 121

      YTO -> CUN, round trip, Oct 17 - 24, $408, United

5. BUG FIXED — the CSV changed the travel DAY of evening / early-morning flights (UTC conversion)
Problem:
- snapshots_to_dataframe() converts departure_at / return_at to UTC (pd.to_datetime(..., utc=True)).
  Same moment in time, but the DATE can move to another day:
      raw JSON (Toronto):  2027-01-31T22:45:00-05:00   -> Jan 31, 22:45
      CSV (UTC):           2027-02-01 03:45:00+00:00   -> Feb 1        <- wrong travel day
- Date format of every field (raw JSON):
                     prices_for_dates                 month-matrix   calendar
      departure_at   local Toronto time (-04 / -05)   date only      local Toronto time
      return_at      local time of the RETURN city    date only      (one-way only)
                     (Tokyo +09:00, Delhi +05:30, London Z ...)
      found_at       UTC (Z)                          UTC (Z)        -
      expires_at     -                                -              UTC (Z)
      fetched_at     UTC (our clock)                  UTC            UTC
- So the shift goes both ways:
      behind UTC (Toronto, Vancouver ...):  evening flights      -> NEXT day
      ahead of UTC (Tokyo, Hong Kong ...):  early-morning flights -> PREVIOUS day
          e.g. Tokyo return 2026-11-20T08:40:00+09:00 -> CSV Nov 19, 23:40

Impact (Oct 06 fetch):
- 199 of 751 departures (prices_for_dates + calendar) on the wrong day in the CSV.
- 72 of 416 returns on the wrong day (52 next day, 20 previous day).
- A Jan 31 London flight showed up as February 2027 (outside the Oct - Jan fetch window).
- Day of week, days before departure, cheapest per day, stay length, and matching
  prices_for_dates with month-matrix (date only) were all off by a day for those rows.
- month-matrix itself was not affected (date only -> midnight UTC -> same day).

ACTION:
  - Keep departure_at / return_at as they are (UTC = exact moment, fine for sorting).
  - File: `src/ingestion/normalizer.py` -> new columns, taken from the RAW text before the UTC conversion:
        departure_date   departure_at[:10]          2027-01-31   (local travel day)
        return_date      return_at[:10]             2026-11-20   (empty for one-way)
        stay_days        return_date - departure_date   7        (empty for one-way)
        departure_hour   departure_at[11:13]        22           (local hour; empty for month-matrix, day only)
    Raw values always START with the local day, so [:10] is right for every endpoint.
  - Computed in canonicalize_snapshot(), only when missing.
  - Safeguard: text that pandas already turned into UTC (`2027-02-01 03:45:00+00:00`, space instead of T)
    is refused -> left empty instead of a wrong day. (write_snapshots_csv() re-reads old CSV rows
    when the header changes; those rows hold UTC text.)
  - Tests added: test_local_dates_survive_utc_conversion, test_local_date_refuses_utc_text. Tests 15/15 pass.

Result (snapshots.csv rebuilt from data/snapshots/1791306228.json):
  - 1379 rows x 26 columns (4 new). Old columns unchanged.
  - departure_date == raw departure_at[:10] for 1379 / 1379 rows; same for return_date.
  - No February 2027 departure anymore (Jan 31 London flight back in January).
  - stay_days: filled for every round trip, empty for every one-way, never negative.
  - departure_hour: prices_for_dates 740/740, calendar 11/11, month-matrix 0/628 (day only).

How to use:
  - anything about the DAY (day of week, days before departure, cheapest per day, stay length,
    comparing endpoints) -> departure_date / return_date / stay_days
  - anything about the exact moment -> departure_at / return_at (UTC)
  - departure_hour -> local time-of-day feature (red-eye / early flights)
